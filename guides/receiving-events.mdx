VOLLEY OSA uses AsyncAPI channels to push real-time data to your integration without requiring you to poll the REST API. Two channels are available: `payload.events`, which delivers discrete lifecycle and state-change notifications, and `payload.telemetry`, which carries a continuous stream of sensor readings from active payloads. Understanding both channels and how to subscribe to them is essential for building integrations that react to payload behavior in real time.

## Two Channels

**`payload.events`** delivers discrete, event-driven messages that describe significant state transitions in the payload lifecycle. Examples include:

- `command_completed` — a dispatched command finished executing successfully.
- `command_failed` — a dispatched command encountered an error during execution.
- `status_changed` — the payload transitioned to a new operational status (e.g., `active`, `idle`, `error`).
- `error` — the payload reported an unrecoverable fault condition.

Use `payload.events` to track command outcomes, monitor payload health, and trigger downstream workflows in your integration.

**`payload.telemetry`** delivers a continuous, high-frequency stream of sensor data emitted by the payload during active operation. The schema of each telemetry message varies by payload type — an RF payload emits signal strength and frequency data, while an electro-optical payload emits frame metadata. Use `payload.telemetry` when you need to ingest raw sensor output for logging, visualisation, or processing pipelines.

## Connecting to AsyncAPI

VOLLEY OSA AsyncAPI channels are available over two transports. Choose the one that fits your infrastructure.

- **WebSocket:** Connect to `wss://async.volleyosa.dev/v1/{channel}` and pass your Bearer token as the `Authorization` header during the upgrade handshake, or as the `token` query parameter if your client does not support custom upgrade headers.
- **AMQP:** Connect to the VOLLEY OSA AMQP broker and pass your Bearer token as the value of the `authorization` key in the connection properties. Exchange and queue binding details are provided by your VOLLEY platform administrator.

All messages on both transports are JSON-encoded UTF-8 strings.

## Subscribing to Events

The example below uses the Node.js `ws` library to connect to the `payload.events` channel over WebSocket and log incoming events to the console.

```javascript
const WebSocket = require('ws');

const ws = new WebSocket(
  'wss://async.volleyosa.dev/v1/payload.events',
  { headers: { Authorization: 'Bearer YOUR_API_KEY' } }
);

ws.on('open', () => {
  console.log('Connected to payload.events channel');
});

ws.on('message', (data) => {
  const event = JSON.parse(data);
  console.log('Event type:', event.type);
  console.log('Payload ID:', event.payload_id);
  console.log('Timestamp:', event.timestamp);
  console.log('Data:', JSON.stringify(event.data, null, 2));
});

ws.on('close', (code, reason) => {
  console.warn(`Connection closed: ${code} ${reason}`);
  // Implement reconnection logic here for production use
});

ws.on('error', (err) => {
  console.error('WebSocket error:', err.message);
});
```

Replace `YOUR_API_KEY` with a valid VOLLEY OSA API key. The connection is established with a single HTTP upgrade request; no additional subscription message is required after the socket opens.

## Event Object Schema

Every message published on `payload.events` follows this structure.

<ResponseField name="type" type="string">
  The event type identifier. Describes what happened, e.g., `command_completed`, `command_failed`, `status_changed`, or `error`. Your handler logic should switch on this field.
</ResponseField>

<ResponseField name="payload_id" type="string">
  The unique identifier of the payload that emitted the event. Use this field to associate events with specific registered payloads in your system.
</ResponseField>

<ResponseField name="timestamp" type="string">
  The ISO 8601 UTC timestamp at which the event was generated by the payload or platform, e.g., `2024-11-14T11:05:55.321Z`. Use this for ordering and deduplication, not the time your client received the message.
</ResponseField>

<ResponseField name="data" type="object">
  An event-specific payload object whose structure depends on `type`. For `command_completed` events, `data` includes `command_id` and `output`. For `status_changed` events, `data` includes `previous_status` and `new_status`. Consult the AsyncAPI specification for the full schema per event type.
</ResponseField>

An example `command_completed` event message:

```json
{
  "type": "command_completed",
  "payload_id": "pl_7f3a9c2b",
  "timestamp": "2024-11-14T11:05:55.321Z",
  "data": {
    "command_id": "cmd_4a1b8e3f",
    "command_type": "START_CAPTURE",
    "output": {
      "frames_captured": 450,
      "data_ref": "capture://pl_7f3a9c2b/cmd_4a1b8e3f"
    }
  }
}
```

## Telemetry Data

Subscribe to `payload.telemetry` using the same WebSocket or AMQP connection pattern. Telemetry messages arrive at the payload's native reporting rate, which can range from a few messages per second to hundreds depending on payload type and configuration.

```javascript
const ws = new WebSocket(
  'wss://async.volleyosa.dev/v1/payload.telemetry',
  { headers: { Authorization: 'Bearer YOUR_API_KEY' } }
);

ws.on('message', (data) => {
  const reading = JSON.parse(data);
  console.log('Payload:', reading.payload_id);
  console.log('Telemetry:', JSON.stringify(reading.data, null, 2));
});
```

An example telemetry message from an RF payload:

```json
{
  "payload_id": "pl_7f3a9c2b",
  "timestamp": "2024-11-14T11:06:01.104Z",
  "data": {
    "frequency_mhz": 433.92,
    "signal_strength_dbm": -72.4,
    "bearing_degrees": 214.5,
    "snr_db": 18.2
  }
}
```

Be prepared to handle back-pressure if your consumer processes messages more slowly than the payload emits them. Consider buffering incoming telemetry or sampling it at a reduced rate if downstream processing is the bottleneck.

## Filtering by Payload

If your integration manages multiple payloads, you can receive events for a specific payload only by appending the `payload_id` query parameter to the channel URL. This reduces message volume and simplifies your handler logic.

```javascript
const ws = new WebSocket(
  'wss://async.volleyosa.dev/v1/payload.events?payload_id=pl_7f3a9c2b',
  { headers: { Authorization: 'Bearer YOUR_API_KEY' } }
);
```

The same filter is available on the `payload.telemetry` channel. You may specify a single `payload_id` per connection; to subscribe to events from multiple specific payloads, open one filtered connection per payload or use an unfiltered connection and filter client-side.

<Tip>
Always implement reconnection logic in production deployments. Network interruptions, platform maintenance windows, and authentication token rotations can all cause WebSocket connections to close unexpectedly. Use an exponential back-off strategy — starting at one second and capping at around 60 seconds — to reconnect without overwhelming the server. Re-authenticate with a fresh token on each reconnection attempt to handle cases where the session was closed due to token expiry.
</Tip>
